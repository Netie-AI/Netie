# GPT conversion and UX critique

- Date: 2026-08-22 UTC
- Model: GPT
- Scope: credibility, hierarchy, static-page implementation, mobile conversion
- Keywords: Jian Hong Oo, Penang AI engineer, internal operations system, cited document search, approval-gated automation, file analytics, static business website, private AI deployment, public demos, Netie
- Main idea: Sell clearly scoped services through verifiable public work and written boundaries. Do not present interface concepts as production, customer, performance, security, or revenue evidence.

## Top conversion and credibility issues

1. The linked main-site proof contains unsupported enterprise / performance assertions, so it should not be the default proof destination.
2. CSS bars and nodes are illustrations, not screenshots, and conflict with an evidence-led page.
3. RM20,000 Checkout appears before a scope confirmation, even though serious system buyers need written deliverables and exclusions first.
4. Some demos do not prove the services they were attached to: AIM/Cortex do not establish a production operations system, and Constructor/Cassandra do not prove delivered analytics.
5. The positioning is a technology list instead of a buyer problem.
6. It is unclear whether Netie is a team or Jian is the accountable delivery person.
7. Service boundaries omit migration, integrations, hosting, API costs, maintenance, acceptance, and data handling.
8. AIM, ASA, and Cassandra are concept or pre-order interfaces, not customer case studies.
9. Employer work and Netie public interfaces should never be conflated.
10. A `mailto:`-only form is fragile on mobile and must not look like a server-side submission.

## Recommended hierarchy

1. Hero - Jian, location, concrete work, main brief CTA.
2. Services - three fixed-price offers plus bounded quoted services.
3. Public work - real screenshots, live links, and evidence limitations.
4. How it works - non-sensitive brief, written scope, delivery.
5. Brief and contact - structured qualification form, email, phone, WhatsApp.

Remove the long product chronology and the separate eight-card artificial demo gallery.

## Screenshot use rules

1. Replace every CSS mock with a real capture of the linked public page.
2. Pair every screenshot with a clickable complete URL and clear caption.
3. State only what the screenshot proves.
4. Label a marketing-page concept, browser-only sketch, or illustrative interface as such.
5. Do not use screenshots as evidence of security, performance, integrations, customer adoption, or revenue.
6. Do not show employer-internal systems, customer data, credentials, or logged-in payment screens.
7. Link each image to the live page and remove it if the link breaks.
8. Do not use ASA as generalized service proof without saying that it is an unreleased pre-order page.
9. If no truthful public example matches a service, state `No public case study` rather than using an unrelated image.
10. Store optimized screenshot files locally instead of hotlinking another site.

## Portable static page checklist

- Canonical page remains `/hire/index.html`.
- Use local relative images such as `./assets/constructor.webp`.
- Keep system fonts and dependency-free HTML/CSS/JS.
- Use single column below 720px; test 320px, 375px, 768px, 1280px.
- Controls need >=44px touch targets. Navigation must wrap.
- Screenshot images need explicit width, height, useful `alt`, `loading="lazy"` below the fold, and `rel="noopener"` on links.
- Visible keyboard focus, semantic headings, labels, and contrast are mandatory.
- Email and `tel:` links must work without JavaScript.
- The mail-composing script is an enhancement only. Never display a false sent state.
- Keep only confirmed Stripe links. Gate RM20,000 payment behind scope confirmation.
- Avoid trackers, chat widgets, custom-font downloads, and paid dependencies.
- Telegraph is a copy adaptation, not a literal static-page mirror.
