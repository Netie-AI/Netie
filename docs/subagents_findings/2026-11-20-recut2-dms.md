## F3. The first relation reader could not see `TABLE t`, and the naive name match could not see quoting

- **Expected:** a granted read serves; a read outside the grant abstains.
- **Actual (measured, probe `probe2.py`, output kept in this finding's Measured section):** the audit
  parser `tables_read_checked("TABLE inventory")` returns `()`, so a guard built on it alone abstains
  on `WITH c AS (TABLE inventory) SELECT COUNT(*) AS n FROM c`, which dms serves (sibling test
  `tests/test_grant_struct_02.py::test_granted_reads_still_serve_exact_rows[...TABLE inventory...]`,
  first targeted run: 1 failed, 263 passed). The shipped guard matched table names by word boundary and
  abstains on `SELECT n FROM bronze."01_clean_sales"` with grant `bronze.01_clean_sales`
  (`ORIG ... -> ABSTAIN space s cannot read`). That is the conflict the earlier lost run saw with
  `test_digit_leading_uploads_are_askable` (`tests/test_grant_struct_02.py` around 1030 to 1075).
- **Repro:** `probe2.py` in the scratchpad (kept as text below). Re-cut: the gate reads relations with
  DuckDB's parse unioned with the audit parser, maps each to the grant that opens it by dms's own
  `relation_gap` key, and hands `answer_or_abstain` a restatement (`SELECT 1 FROM <granted names>`).
  A relation no grant opens is passed as a known-but-ungranted name so the gate sees it.
- **Result:** both sibling tests pass unchanged, so no sibling test is edited, skipped or deleted and
  this is not a decision memo case. `TABLE transactions` against grant `inventory` abstains in the
  gate, and `serve_gap` refuses it as `hostile_sql:statement_not_allowed`.
  Note for dms (not changed here): `name_echo.served_ungranted` reads relations with the same audit
  parser, so for `sql_used = "TABLE transactions"` it returns `[]`; only `serve_gap` upstream stops it.
- **Root-cause class:** two relation readers with different blind spots, one of them used as a gate.
- **Invariant:** read the statement with the engine that runs it, and fail closed when nothing is read.

## Decision memo: the 12000-character answer cap now applies on every path

- **Behaviour A (patch, Netie `answer_or_abstain` `MAX_ANSWER_CHARS = 12000`, "DitchContext"):** a
  Space-scoped answer whose rows serialize past 12000 characters abstains `space_acl`. It was already
  true on the contract-ask lane; it is now true on all of them and on `answer_user_sql`.
- **Behaviour B (dms today):** rows of any size are returned (up to the lane's own LIMIT).
- **Evidence:** probe, `guard_live_answer` on 50, 150 and 300 three-column rows (2941, 8891 and 17891
  characters): OK, OK, `ABSTAIN answer over DitchContext`. No dms test in the base or patched run
  failed for this (see Measured); no sibling test pins a result larger than the cap inside a Space.
- **User-facing cost on dms's own demo questions (measured by the T1 verifier, not the builder):**
  dms has no runnable demo question fixture, so the set was the 6 `SUGGESTIONS` in `demo_ask.py`, the
  7 distinct questions dms's tests pass to `demo_ask`, and 3 added top-N stress questions (14
  distinct after dedupe). Each ran through `Executor.demo_ask` in a Space granting all 6 demo tables,
  unpatched against patched. Same answers on both: 3 abstain on both (alerts, meaning of life,
  forecast), none because of the cap. New abstains on the patched side: 0 for the cap, 0 for any
  other reason. Largest rows payload: 286 characters. So on the demo set the cap costs nothing today;
  a large export-style question in a real Space is where it would bite (the 300-row probe above).
- **Options:** (1) keep Netie's 12000 on every path (current); (2) a larger dms cap through the
  `max_chars` parameter that `guard_live_answer` now takes (no netie change needed); (3) no cap on
  `answer_user_sql` only.
- **Recommendation:** (1) until a customer result trips it, then (2) with a stated number. The 12000 is
  AirGPT's chat-context budget, not a dms limit, so this is a product number the founder sets.
  I did not choose a number.
